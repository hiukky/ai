## The direction is fixed

A tool installed by hand exists exactly until the next machine, and nobody finds
out which ones those were until they are setting one up. So every change flows
one way: **written into the chezmoi source directory, then performed on the
machine by `chezmoi apply`.**

That is chezmoi's own documented flow (`chezmoi edit --apply`). The opposite,
`chezmoi add` and `chezmoi re-add`, is an import path for what already happened
on disk, not a workflow to plan around.

`sudo apt install`, `brew install`, `npm i -g`, `curl | sh`, editing a shell rc
in place: none of those are how something *gets onto* a machine. Running one to
try it out is fine. The task is not done until the same thing is expressed in
the source and would be reproduced by an apply on a clean machine.

## It reads your setup, it does not assume it

The skill opens by looking: where `chezmoi source-path` actually points, which
lanes exist under `.chezmoiscripts/`, what `chezmoi data` says about the
platform, and what the source directory's own `CLAUDE.md` or `AGENTS.md`
already decided. **A setup's own documented conventions win over the skill.**

Which means it never hardcodes a package manager, a filename or a numbering
scheme. It classifies the change by *kind* and goes looking for that kind's
existing home:

| Kind of change | Where it belongs |
| --- | --- |
| OS package | the existing package-list script — a package is a line, not a script |
| a runtime a declarative version manager can install | that manager's config |
| tool with an official installer or a release binary | a new guarded `run_once_before_` script |
| tool needing an applied dotfile or a runtime from earlier in the same apply | a `run_once_after_` script |
| software for a host machine (guest → host) | that host's script, behind a platform probe |
| a file outside chezmoi's target directory | `.chezmoitemplates/` + a `run_onchange_` script |
| a config file the tool reads | `chezmoi add`, `.tmpl` when it is machine-specific |
| generated state, caches, credentials | nowhere — tracking it makes the next machine wrong |

Ordering is dependency order, read off the neighbouring numbers rather than
invented. Scripts are guarded with `command -v` because `run_once_` is tracked
by a hash of its contents: editing one re-arms it, whole, on the next apply.

## "Is it in sync?" is four questions

A green answer to one is not an answer to the others.

1. **Machine vs source** — `chezmoi status`, `chezmoi verify`
2. **Source vs committed** — `git status` in the source directory
3. **Committed vs pushed** — a commit on one machine is not a provisioned fleet
4. **Installed vs provisioned** — what is on `PATH` that no lane installs

The fourth has no command, because it depends on which managers the machine
actually uses — so the skill asks each of them what was installed deliberately
and diffs that against the lanes. It is also the one that bites: it is the gap
between a machine that works and a machine that can be rebuilt.

## What an apply quietly deletes

The most common regression is an installer appending to a file chezmoi manages —
a `PATH` line written into a shell rc by some tool's installer. The source knows
nothing about it, so `chezmoi apply` removes it, silently, as part of doing its
job correctly.

Hence the rule the skill enforces: read `chezmoi diff` for **removals** before
every apply, and move anything that should survive into the tracked file rather
than leaving it on the machine.

## Guardrails

A dotfiles repo is assumed public and `chezmoi add` copies content verbatim, so
anything being added gets read for credentials first — including the credential
files of whatever tools that setup installs. `chezmoi init` is never run on an
already-provisioned machine: it rewrites the config from a template that usually
defines only `[data]`, dropping hand-set keys like `sourceDir`, which is how a
machine ends up with a second, divergent clone of its own dotfiles. And the
steps that genuinely need a person — key generation, browser logins, a first-boot
account — stay at the end of provisioning, announced rather than scripted around.

## Reclaiming disk space

The other way a machine drifts is by filling up. The `reclaim` skill splits the
job the same way the rest of this plugin does: what is deterministic is a
script, what needs a person stays with the person.

| Step | Deterministic | Who decides |
| --- | --- | --- |
| `reclaim scan` | measures the Linux side, every WSL virtual disk (allocated size, sparse or not, space already free inside it) and the Windows host's folders, in one pass | nobody — it changes nothing |
| `reclaim prune docker\|caches\|build` | removes only what a tool rebuilds on its own: docker build cache and unused images, package-manager caches through their own clean commands, cargo `target/` and `node_modules/` | the person, once, after the dry run |
| judgement items | worktrees (branch, merged, uncommitted files, age), docker volumes, downloaded models, emulator and VM images, the hibernation file | the person, item by item |
| `reclaim compact` | prints `fstrim`, `wsl --shutdown`, a one-time `--set-sparse` and a `diskpart` compaction with this machine's distro and disk path filled in | the person runs it — shutting WSL down would stop the agent too |

A WSL disk never gives space back on its own unless it is sparse, so what was
pruned inside the distro only reaches the host after compaction. That is why
compaction is always the last thing the skill prints.
