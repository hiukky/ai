## The direction is fixed

A tool installed by hand exists exactly until the next machine, and nobody finds
out which ones those were until they are setting one up. So every change flows
one way: **written into the chezmoi source directory, then performed on the
machine by `chezmoi apply`.**

That is chezmoi's own documented flow (`chezmoi edit --apply`). The reverse,
`chezmoi add` and `chezmoi re-add`, is an import path for what already happened
on disk, not a workflow to plan around.

`sudo apt install`, `npm i -g`, `curl | sh`, `winget install`, editing `~/.zshrc`
in place: none of those are how something *gets onto* the machine. Running one
to try something out is fine. The task is not done until the same thing is
expressed in the source and reproduced by an apply on a clean machine.

## Every change has a lane

The skill's job on "install X" is picking the right one, then guarding it.

| What arrived | Lane |
| --- | --- |
| apt package | the apt list script — a package is a line, not a script |
| something mise has a backend for | `config.toml` `[tools]` |
| tool with an official installer | a new guarded `run_once_before_NN-*.sh` |
| tool needing an applied file or a mise runtime | a `run_once_after_8N-*.sh` |
| Windows-host desktop app | the winget/Store script, through `powershell.exe` |
| a Windows-side file outside `$HOME` | `.chezmoitemplates/` + a `run_onchange_` script |
| a config file the tool reads | `chezmoi add`, `.tmpl` when it is machine-specific |
| generated state, caches, credentials | nowhere — tracking it makes the next machine wrong |

Numbering is dependency order, not taste. Scripts are guarded with `command -v`
because `run_once_` is tracked by content hash: editing one re-arms it, whole,
on the next apply.

## "Is it in sync?" is four questions

A green answer to one is not an answer to the others.

1. **Machine vs source** — `chezmoi status`, `chezmoi verify`
2. **Source vs committed** — `git status` in the source dir
3. **Committed vs pushed** — a commit on one machine is not a provisioned fleet
4. **Installed vs provisioned** — what is on `PATH` that no script installs

The fourth has no command and is the one that actually bites: it is the gap
between a machine that works and a machine that can be rebuilt.

## What an apply quietly deletes

The most common regression is an installer appending to a file chezmoi manages —
a `PATH` line written into `~/.zshrc` by some tool's installer. The source knows
nothing about it, so `chezmoi apply` removes it, silently, as part of doing its
job correctly.

Hence the rule the skill enforces: read `chezmoi diff` for **removals** before
every apply, and move anything that should survive into the tracked file rather
than leaving it on the machine.

## Guardrails

The repo is public and `chezmoi add` copies content verbatim, so credentials get
checked for before anything is added. `chezmoi init` is never run on an
already-provisioned machine — it rewrites the config from a template that does
not define `sourceDir`, which is how a machine ends up with a second, divergent
clone of its own dotfiles. And the interactive tail of provisioning — SSH keys,
`gh`/`claude` logins — stays interactive on purpose.
