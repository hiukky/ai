## Three artifacts

| Artifact | Answers | Lives in |
| --- | --- | --- |
| **OpenSpec change** | What are we changing now? | `openspec/changes/<name>/` |
| **ADR** | Why is the system this way? | `docs/adr/NNN-*.md` |
| **Architecture** | How is the system organized? | the directory the project declares |

## The flow

1. **Propose.** A change gets `proposal.md`, `specs/`, `design.md` and
   `tasks.md`. Decisions that might deserve a record go under
   `## Candidate ADRs` in the design.
2. **Apply.** The tasks are worked. What the plan didn't decide goes in the
   change's `decisions.md`. A change that moves a boundary updates its
   architecture diagram in the same change.
3. **Archive.** Only now are ADRs written, and only for candidates that pass
   all four questions:
   - Is reversing it expensive?
   - Was a real alternative rejected?
   - Does it bind code that doesn't exist yet?
   - Is it recorded nowhere else?

Most changes produce no ADR. Naming, refactors, bug fixes and version bumps
never do.

## Run it unattended

`auto` works the whole task list without you: verifies each item by exit code,
commits one at a time, and writes every decision down for you to review. It
stops for five things only:

- a destructive action outside the change
- a step that would break a spec
- three failed attempts at one task
- a credential or a leaked secret
- a finding that kills the proposal's premise

## Adopting it

`init` is **user only**: it writes `openspec/`, `docs/adr/` and the schema into
your repository, so it runs when you call it and never on its own. Every step
checks before writing, and running it again is safe.
